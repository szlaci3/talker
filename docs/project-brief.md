## User requirements

- Target standard desktop browsers for the chat and WebMCP experience; voice input must also work on mobile. Support headphones and speakers, including a phone's built-in microphone. Feature and recognition support vary by browser/device; provide a clear fallback when voice input is unsupported. When WebMCP is unavailable, display a notice and continue with the best available fallbacks. Native WebMCP is not required in every browser; coverage is partial, unknown, and accepted.
- Initially one chat screen, visually familiar to ChatGPT, one conversation, no sidebars. Typed messages and answers form the first MVP.
- Invitation-code submission must show immediate loading feedback after Enter or Continue, including while the backend wakes up.
- General-purpose assistant with suggested prompts demonstrating conversational UI changes (user accepted this recommendation).
- Users can request theme and font-size changes, plus natural-language color changes for named UI areas: page/header/message/input backgrounds, main/secondary/input text, and accents. Follow-ups such as “that red is too dark” should adjust the last color target. Do not implement arbitrary UI changes, typography styles, or generated CSS/JavaScript.
- Voice output uses `edge-tts`, following the voice experience in the user's Reciter website: browser Daniel during warmup, then preferably Microsoft Brian Multilingual Online (Natural) - English (United States). The live catalogue and synthesis verified `en-US-BrianMultilingualNeural`; the user verified Brian playback and browser-voice fallback in desktop Edge/Chrome, with good English and Hungarian output. The specific Daniel fallback identity remains unconfirmed. Later voice input must show evolving transcription while the user speaks, without waiting for dictation to finish before displaying text.
- Voice input v1: use Gemini 3.5 Transcribe Live for the full dictation, with automatic language detection and live transcript updates. Use browser speech recognition in English only when Live fails or cannot continue; it is not the normal recognition path. ASR must be free of charge; do not use a billable tier or silently fall back to paid usage. Frontend UX handles provider errors, including quota/concurrency errors; do not add a server-side maximum of three Gemini requests per minute. The portfolio assumes one user at a time. Do not display a detected-language/refresh-to-switch notice. Dictation appends to existing composer text and continues through pauses. Mic becomes Mute immediately, including during connection setup; Mute stops recognition and releases the microphone without submitting or clearing the draft, then becomes Mic again. Send also ends recognition and submits the draft. The same control is labeled “Interrupt” while an answer is generating or playing; clicking it cancels generation or stops playback and starts microphone input. Keep answer speech's current manual Play workflow. Highlight transcript corrections with `#ffdd00` for five seconds. Use the existing server-side Google API key/project; never expose it in the browser. Any free-tier quota must fail closed rather than incur charges.
- Audio setup: support both headphones and speakers. On mobile, the user may prefer the device's built-in microphone over an attached headset microphone. Because recognition is only started by Mic/Interrupt, stop assistant generation/playback before starting it.
- Voice input/output v2 (future): after activation, submit the latest transcript after four seconds of silence; “Send now” submits early. Recognition revisions do not restart the silence timer. Display “Listening” until the final two seconds, then show the countdown. The eventual speech-output target is incremental: synthesize and play the first available words, then subsequent text in the existing speech chunk sizes as the answer grows. Do not include these v2 behaviors in the initial voice-input implementation.
- Use the Antigravity managed agent as the production provider. The user reports higher daily and per-minute token quotas for it than for direct Gemini and has decided not to implement Gemini fallback.
- Host the frontend on Netlify; the user favors a Render backend for the server-side API and `edge-tts`.
- Add light entry friction against bots. The proposed code starts at 11 and increments daily beyond 99; typing the current date was another possibility. The mechanism remains open for review.

## Recommended architecture

Use React + TypeScript + Vite and simple CSS variables for appearance on Netlify. Recommend a Python `aiohttp` API on Render to host `edge-tts` and Google requests together, reusing Reciter's backend approach; a separate Node server is unnecessary. This supersedes the initial Netlify Functions recommendation following the user's explicit `edge-tts` choice. React helps coordinate streaming messages, speech state, preferences, and tool-driven updates. Vanilla TypeScript offers no WebMCP compatibility advantage.

Flow: Netlify browser chat -> Render API -> Antigravity -> streamed answer/tool request -> browser validates and executes a known UI action -> tool result returns to the model when needed. No Gemini fallback is planned. Speech: completed text segments -> Render `edge-tts` -> browser audio playback. Configure allowed frontend origins and a working session transport; CORS is not authentication. Direct cross-site calls versus a same-origin proxy remains an implementation choice to validate for streaming and cookies.

Keep the Google key in Render server environment variables, never in the browser bundle, browser storage, or a VITE-prefixed variable. Backend responsibilities: entry/session validation, request limits for chat and TTS, input/context/output bounds, provider calls, timeouts, cancellation, and useful quota errors. Initial chat history lives only in page state and clears on reload. Antigravity interaction IDs are bound to a per-page conversation ID, separate from the access token, so reload begins a new model conversation. No conversation database is used. Shared usage counters require platform enforcement or durable storage rather than restart-sensitive process memory.

Use one small action registry: `set_theme`, `set_font_scale`, `set_ui_color`, `get_ui_preferences`, and `reset_ui`. Validate enumerations, numeric bounds, color targets, and hex colors. Manual controls, Antigravity function calls, and WebMCP registration share the same handlers, updating React state and CSS variables. Persist appearance locally, keep actions reversible, and provide a reset. Adjust foreground colors to preserve readable contrast when possible, and report when conflicting custom surfaces prevent the target contrast. Do not allow arbitrary generated scripts, markup, or styles.

## WebMCP feasibility

WebMCP is an evolving browser proposal, usable as progressive enhancement. It exposes structured tools on the live page; it does not supply the LLM or automatically connect a cloud model to the visitor's tab. The current draft uses `document.modelContext`, with tool registration, discovery, and execution APIs; older examples use `navigator.modelContext`. Verify the target browser implementation rather than blindly copying either version. See the [Chrome guide](https://developer.chrome.com/docs/ai/webmcp) and [current draft](https://webmachinelearning.github.io/webmcp/).

Expose the shared actions through the current `document.modelContext` API. When available, route in-page assistant appearance calls through `getTools()` and `executeTool()`; otherwise invoke the same validated handlers directly. Registration exposes the tools to browser agents out of band, but does not connect an external agent or provide an LLM. The user explicitly accepts fallbacks: show a nonblocking availability notice and keep the application working as well as possible. Do not label ordinary function calling as native WebMCP. A portfolio claim of native WebMCP still requires demonstrated registration and invocation in a supported browser/agent. HTTPS, origin isolation, and permissions policy need verification; universal native browser support is no longer a requirement.

## Google model choice

Google currently documents `antigravity-preview-09-2026`, defaulting to `gemini-3.8-flash`, with free- and paid-tier API access. It is a managed agent with a remote sandbox and potentially long autonomous workflows. This is distinct from a direct model call and from an IDE subscription. See [Antigravity API](https://ai.google.dev/gemini-api/docs/antigravity-agent).

The user's quota comparison is account-specific and user-reported. Direct Gemini fallback is explicitly out of scope. The user reports 28 requests in one day without quota errors; this does not establish the provider's full daily limit. The Antigravity API uses the Interactions endpoint and agent ID `antigravity-preview-09-2026`; it is not a Gemini model ID for `GOOGLE_MODEL`. The agent currently defaults to Gemini 3.8 Flash under its managed harness, with a separate supported-model setting. The app overrides default agent tools with only its validated appearance functions; it does not enable code execution, browsing, or filesystem tools. Each turn remains in backend-managed interaction state. See the [managed agents quickstart](https://ai.google.dev/gemini-api/docs/managed-agents-quickstart) and [streaming guide](https://ai.google.dev/gemini-api/docs/streaming).

Actual model access and free quotas must be checked in the user's Google AI Studio project. Quotas are shared per project, not multiplied per visitor or API key; published limits do not guarantee capacity. Provide an explicit exhausted-quota state and bounded retries. See [rate limits](https://ai.google.dev/gemini-api/docs/rate-limits).

## Voice feasibility

Output decision: use server-side `edge-tts`, a Python client for Edge's online speech service. It does not require visitors to run Edge or Windows. The browser plays returned audio. This replaces the earlier browser-synthesis-first proposal. See the [edge-tts project](https://github.com/rany2/edge-tts).

Reference inspected on 2026-09-25: `C:\Users\szala\Planets\Reciter`. Relevant files: `edge-speech.js` (warmup, prefetch, playback, cancellation), `speech.js` (segmentation), `app.js` (voice selection), `server.py` (`aiohttp` API), `render.yaml`, and `DEPLOY-RENDER.md`. Its requirements pin `edge-tts==7.2.8` and `aiohttp==3.14.3`. The deployment note reports prior successful Netlify/Render use; this task performed code review only, not a live deployment or listening test. Reciter was not modified.

Voice policy: prefer Microsoft Brian Multilingual Online (Natural) - English (United States) immediately when available; Daniel is a temporary warmup/fallback voice, not a compulsory first utterance. Reciter selects browser-provided Daniel (British English, preferred pitch 1.4); it is not an `edge-tts` voice identifier and is not available on every device. Reciter's current remote default is `en-GB-SoniaNeural`; this project's requested remote voice is Brian. Resolve Brian from the service catalogue and do not silently substitute a similar remote voice. If Daniel is absent, report the browser default voice accurately.

Connection recovery decision (2026-09-27): allow one automatic complete Reconnect operation per new Play after a temporary catalogue/network/synthesis failure. Keep the existing bounded requests within that operation. The initial connection does not consume the allowance; manual or automatic Reconnect does. Pause/Resume preserves it, with new automatic recovery deferred while paused. Browser speech continues during recovery and Brian joins at an unread segment boundary. Stop, playback completion, or another Play invalidates old recovery; manual Reconnect remains available after automatic recovery fails. Do not automatically reconnect for authentication, quota, or browser playback-permission errors.

Reuse Reciter's behavior: bounded readiness retries while Daniel continues; prefetch one upcoming segment; switch only at an unread segment boundary when matching audio is ready; retain segmentation across the handoff; cancel stale requests/audio on Stop. Its connection checks allow six 12-second attempts with five 3-second delays, and speech requests retry a 502 once. Adapt passage-level recovery to assistant messages. Retain play/pause/resume and browser playback-permission handling; mobile-specific work is out of scope. Prefer Brian for every segment once ready. User-selected cold-start browser lead (2026-09-30): one segment, reduced from three; prepare Brian for segment two while the browser speaks segment one. Reciter buffers complete MP3 segments rather than streaming audio bytes to playback; LLM text streaming is separate. Treat upstream failures explicitly; `edge-tts` does not provide speech recognition.

Input architecture: use full-session Gemini 3.5 Transcribe Live. It supports interim/final text, automatic language detection, and code-switching; its dedicated guide limits a session to 10 minutes. Reconnect or resume Live at the session limit while preserving the user's draft; use browser English recognition only if Live fails or cannot resume. Gemini Live uses 16 kHz PCM input; the frontend requests a short-lived, single-use token from the authenticated backend, constrained to the transcription model/configuration. The permanent Google API key remains server-side. Google estimates audio input at 25 tokens/second for pricing, so a continuous one-user stream is about 1,500 audio input tokens per minute; a reported 20,000 input TPM quota is roughly 13 times that one-stream rate. The general quota docs do not specify whether the TPM window is rolling or aligned to wall-clock minutes, so verify in AI Studio and with a steady-stream test. See [Live transcription](https://ai.google.dev/gemini-api/docs/live-api/live-transcribe), [ephemeral tokens](https://ai.google.dev/gemini-api/docs/live-api/ephemeral-tokens), [pricing/token estimate](https://ai.google.dev/gemini-api/docs/pricing), and [rate limits](https://ai.google.dev/gemini-api/docs/rate-limits).

Voice input v1: after the user clicks “Mic”, detect the spoken language automatically and show interim recognition in the composer, updating the same draft as recognition revises it. Aim for the broadest reliable language coverage available from the selected approach; surface an understandable fallback when a language or browser is unsupported. Continue listening through arbitrarily long pauses until the user clicks Mute or Send; silence never submits automatically. Mute preserves the draft and allows Mic to resume by appending to it. Highlight corrected spans with `#ffdd00` for five seconds, update only changed spans, and ensure removed words do not remain in the submitted text. Typed input remains available. The same control is labeled “Interrupt” while the assistant generates or plays an answer; clicking it cancels generation or stops playback, then starts microphone input. Speech output retains the current manual Play workflow.

Version 2, deferred: configurable four-second silence submission, “Send now”, a countdown shown only during the final two seconds, and incremental answer speech that begins playing early chunks while later answer text is still arriving. Transcript-only corrections do not reset the silence timer. These are future goals, not v1 acceptance criteria.

## Hosting and entry friction

Current hosting direction: Netlify static frontend plus Render Python API for Antigravity/Gemini and `edge-tts`. Render's free web services sleep after 15 idle minutes and typically take about one minute to restart. Early readiness requests can overlap startup with entry-code typing, but cannot guarantee Brian is ready immediately. A paid instance avoids idle spindown; no paid plan has been authorized or purchased. See [Render free services](https://render.com/docs/free). Keep the frontend usable during startup and distinguish backend readiness from successful TTS synthesis. Daniel can read existing text while Render sleeps; new model-generated answers also wait for Render if the same backend serves both APIs.

A date or predictable daily counter is light friction, not meaningful bot resistance. Recommend a short random invitation code shared alongside the link, validated server-side, exchanged for an expiring signed session cookie, with limits on both entry attempts and chat requests. Add a global daily usage cap. Exact code format/rotation is undecided. If the daily counter is retained, define its start date and timezone explicitly; never rely on a frontend-only check to protect the Google quota.

Verify each milestone against its behavior before expanding scope. Do not claim voice or native WebMCP support based on documentation alone.

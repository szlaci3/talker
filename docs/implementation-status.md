# Implementation status

- Current milestone: 3, speech output deployed and user-verified, with handoff latency still unresolved; milestones 1 and 2 are deployed and the user reports production chat and appearance controls work. Antigravity remains the sole production chat provider; no Gemini fallback.
- Actual implementation: React + TypeScript + Vite frontend; aiohttp backend; text chat, cancellation, Markdown, validated conversational appearance controls, WebMCP progressive enhancement, and per-answer Play/Pause/Resume/Stop controls. Speech uses the authenticated `/api/voices` and `/api/speech` routes, a bounded MP3 cache, request limits, exact Brian voice selection, one-segment prefetch, and browser Daniel/default speech while the service warms or fails. `edge-tts==7.2.8` is in backend requirements. Browser speech and Brian share the same text segment boundaries so handoffs continue at the next unread segment.
- Checks passed: `npm test` (18 deterministic Vitest/RTL tests); `npm run build`; backend `python -m unittest -v test_speech` (2 route tests); Python AST syntax validation. Live local TTS check found `en-US-BrianMultilingualNeural` in Microsoft's voice catalogue, synthesized a generic sample, and returned it through the authenticated local speech routes as `audio/mpeg` (12,096 bytes). No user text, production chat API, or user API key was used for that sample.
- Speech connection fix (2026-09-26): user reported six catalogue attempts ending in `Failed to execute 'fetch' on 'Window': Illegal invocation`. Native `fetch` was invoked with the speech controller as its receiver, failing before a network request. Bound the default fetcher to `globalThis` for catalogue and synthesis requests. A regression test covers both request receivers through Reconnect. All 19 frontend tests and the production build pass in a temporary Linux copy installed with `npm ci`; workspace dependencies were installed for Windows.
- User playback verification (2026-09-26): Brian readiness and actual playback work in desktop Edge and Chrome, plus Edge on iPhone (incidental coverage; mobile remains out of scope). English and Hungarian speech sound good. Cold starts use browser speech; the user reports needing Reconnect to obtain Brian. Handoff preserves words without omissions, repetitions, or other observed side effects, but introduces 5–14 seconds of silence at “Preparing Brian audio”; new text has the same startup delay. Code inspection confirms cloud selection happens before matching audio is ready, and prefetch starts only during Brian playback, not browser playback.
- Live checks pending: explicit pause/resume and stop verification. WebMCP-specific verification has not been recorded: an agent must invoke a tool registered through the browser's WebMCP API and the page must apply it. Successful chat-driven appearance changes use the direct shared handler and do not establish that route.
- Known limits: speech catalogue and audio cache, chat counters, and usage limits are process-local. The exact Brian service identifier and synthesis were confirmed from the live catalogue/sample; Daniel availability depends on the browser and OS, with its default voice reported when Daniel is absent. Desktop browser/OS coverage is partial, unknown, and accepted; phones are excluded. English and Hungarian output are user-verified; other languages remain unverified. Native WebMCP and milestone 4 hands-free speech input remain incomplete. The user reports 28 chat requests in one day without quota errors; that does not establish the provider's full daily quota.
- Existing fixes confirmed by the user: after refresh, Antigravity no longer remembers an old page conversation; assistant Markdown renders correctly; canceled turns no longer break or mismatch subsequent answers; stale turns remain copyable and visibly marked; dark-mode composer colors and the color-picker surface were visually confirmed. The Bug 5 chained-action fix is implemented and deterministic tests pass; the specific production sequence still needs confirmation. Invalid invitation codes return the expected rejection. A cold Render start took about 30 seconds and then returned a proper answer. The user confirmed Gemini fallback is out of scope.
- Next concrete step: address the 5–14 second speech startup/handoff silence by preparing audio during browser playback and switching only when the matching unread segment is ready; investigate cold-start recovery requiring Reconnect. Browser Use is unavailable in this environment, so browser actions remain user checks.
